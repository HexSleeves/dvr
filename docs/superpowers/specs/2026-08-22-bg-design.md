# bg — a jj-powered repo daemon

**Date:** 2026-08-22
**Status:** Approved design
**Goal:** A daily-driver source-control tool for Jacob and his agent fleets that kills three specific git pains: parallel checkout juggling, commit/branch ceremony, and repo access without a filesystem checkout. Success = stop fighting git day to day.

## Motivation

Git's primitives fight modern workflows, especially agent-heavy ones:

- **Worktrees are clunky.** Creating them is slow (fresh installs of `node_modules`), keeping them current against main is manual, and parallel agents collide with each other's checkouts.
- **Commit ceremony is waste.** Staging, stash, WIP commits, and rebase interruptions force thinking about history mid-flight instead of after the fact. jj's model (working copy is a commit, snapshots are automatic, conflicts are data) is the right one.
- **Repo access requires a full OS.** Agents and sandboxes should be able to read and write repo state with API calls, not a clone + kernel + filesystem.

Explicitly **out of scope**: hosting/forge concerns — visibility and permissions models, private sub-packages in public repos, hidden in-flight PRs. That is a different project.

## Foundation decision

Built on **`jj-lib`** (Rust). This inherits auto-snapshotting, stable change IDs, conflict-as-first-class-data, and the git backend (interop) for free. The new work is the daemon, workspace manager, and API layer — which is exactly where the pain lives. Alternatives considered and rejected: raw git plumbing (more control, much more work, re-invents jj's model) and a custom store with git as a sync target (most ambitious, riskiest interop, wrong for a daily driver).

## 1. Shape

One Rust workspace producing one binary with three faces:

- **`bgd`** — a per-machine daemon embedding `jj-lib`. It owns every registered repo's store and is the **only writer**. Serves JSON over a unix socket with HTTP semantics (`curl --unix-socket` works for debugging).
- **`bg`** — the human CLI, a thin client over the socket. Day-to-day replacement for git/jj commands.
- **`bg mcp`** — an MCP server (stdio) over the same API, exposing repo ops as native tools to Claude Code / agent fleets.

CLI and MCP contain no repo logic; everything goes through the daemon API. The daemon auto-starts on first client call if not running.

## 2. Core model (kills the ceremony)

Inherited from jj, exposed simply:

- The working copy **is** a commit. The daemon watches registered workspaces via FSEvents and snapshots automatically on file change — closing jj's remaining seam where snapshots happen only when a command runs.
- No staging area, no stash, no WIP commits. Every state is always recorded; history is curated afterward, not performed during.
- Stable **change IDs** name units of work; commits are an implementation detail.
- **Conflicts are data**, stored in-history. Nothing ever blocks mid-rebase.

A human needs two verbs: `bg describe` (name what a change is) and `bg push`. Everything else is inspection (`bg st`, `bg log`, `bg diff`).

## 3. Workspaces (kills worktree pain)

- `bg ws new [-r <change>]` materializes a directory via APFS `clonefile` — copy-on-write, milliseconds, and cloning from an existing workspace carries `node_modules`/build caches along for free.
- Any number of workspaces per repo. The same change checked out in two places is allowed.
- The daemon watches all workspaces and auto-snapshots each independently.
- `bg ws new --track main` opts a workspace into auto-rebase when main advances; conflicts are recorded in-history rather than stopping work. (v3)
- Deleting a workspace is just `rm -rf` — every state it ever held is already in the store. `bg ws list` / `bg ws gc` reconcile daemon state with reality.

This is what agent fleets get instead of worktree juggling: spawn N cheap workspaces, let agents work, harvest changes from the store.

## 4. No-checkout API

The daemon exposes repo state directly over the socket:

- **Read:** file contents at any revision, tree listings, log, diff, search.
- **Write:** create or amend a change by POSTing file contents — no workspace, no filesystem involvement. A sandboxed agent holding only the socket can do a full read-modify-describe-push loop.

MCP tools map 1:1 onto this API.

## 5. Git/GitHub interop + guardrails

- jj's git backend underneath: every registered repo remains a real git repo. Plain `git`, editors, and build tools keep working inside workspaces. Push/PR flows to GitHub are unchanged.
- **Guardrail: never auto-push.** No background sync ever touches a remote.
- **Guardrail: no implicit branch tracking.** New changes never silently track a remote branch; `bg push` always states exactly which remote/branch it is writing to and requires the first push to be explicit about its target.

## 6. Build order

- **v1 — daily driver:** `bgd` + `bg` CLI: `register`, `st`, `log`, `describe`, `ws new`, `push`, read-only API. Auto-snapshot watcher. macOS only.
- **v2 — agents online:** write-without-checkout API + `bg mcp` server.
- **v3 — quality of life:** `--track main` auto-rebase, Linux support (reflink/overlayfs in place of `clonefile`).

## Error handling & testing

- Daemon API errors are structured JSON (code + message + hint); the CLI renders them tersely.
- The watcher must be crash-safe: on daemon restart, re-scan workspaces and snapshot any drift before serving requests.
- Testing: unit tests against `jj-lib` operations on temp repos; integration tests drive the daemon over the socket (spawn `bgd` against fixture repos, assert snapshots/workspaces/pushes via the API); `clonefile` behavior gets a small macOS-specific test suite. Push guardrails get explicit tests (no remote write without explicit target).
